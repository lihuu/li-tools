# Project instructions

## Technical baseline

- Java 25 source, Maven, Picocli, GraalVM Native Image. Do not lower the compiler release or add another build system.
- Native executables are the distribution target; use JVM tests and the runnable JAR for fast development.
- Prefer JDK APIs. Add libraries only for a concrete requirement. Use Jackson when JSON is needed; it is deliberately absent until then.
- No Spring, DI framework, classpath scanning, project-owned reflection, runtime Java compilation, or dynamic class loading.
- Construct objects explicitly and use constructor injection. Keep business behavior out of the entry point.

## Scope and code quality

- Communicate in the user's current language. Lead with the outcome; distinguish verified facts, assumptions and unverified checks.
- Inspect available context before asking questions. Continue authorized work; ask only when missing information materially changes scope or risk.
- Search within the current workspace using explicit paths. Do not inspect unrelated directories or private files without explicit authorization.
- Treat the user's objective as closed scope. Inspect relevant code before editing; preserve unrelated work.
- Choose the smallest maintainable change. Do not add interfaces, factories, registries, empty packages, or generic helpers for possible future requirements.
- Do not use `var`, including in tests. Declare local types explicitly.
- Prefer immutable values and explicit ownership; use records for simple data carriers.
- Keep classes focused, methods at one level of abstraction, and public API surface small.
- Prefer clear control flow over clever streams and callback chains. Use Optional mainly as an absence-bearing return value.
- Preserve exception semantics. Do not catch broad Exception, swallow failures, or use exceptions for normal control flow.
- Annotate public reference parameters and return values with JetBrains @NotNull/@Nullable for IDE and static analysis. These annotations do not generate runtime checks. Add explicit validation only when the required behavior calls for it; Objects.requireNonNull is allowed.
- Review changed production code for unnecessary abstraction, duplication, unclear ownership, and excessive indirection after tests are green.

## Source and CLI boundaries

- Multi-module monorepo: `cli-common` provides shared interactive shell and utilities; sub-tools (`gpgkit`, `certkit`, `tokenkit`) implement specific domain logic under `io.github.lihuu.<tool>`.
- `app` owns the entry point and explicit wiring. `cli` owns Picocli parsing, output and exit codes.
- All CLI tools inherit `cli-common` (`CliRunner`, `GlobalOptionsMixin`) for uniform flags and exit code handling.
- Create config, runtime or business packages only when real behavior needs them. Business code must not depend on Picocli or app/cli.
- Keep result output on stdout and errors on stderr. Return 0 for success, 2 for invalid CLI usage, and 1 for execution failures unless a command documents another contract.
- Provide --help and --version. Bare invocation shows help. Support inherited --no-color and presence-based NO_COLOR; redirected output and usage errors must have no ANSI escapes.
- Root pom.xml is the project version source. application.properties is Maven-filtered; never hard-code the project version in Java or tests.
- Library reflection/resources/JNI/proxies require narrowly scoped Native metadata and verification with the native executable. Picocli metadata is generated by picocli-codegen.

## Development and verification

- Use TDD for behavior changes: one failing behavioral test, confirm the expected failure, implement the minimum fix, rerun it and directly affected tests.
- Test public behavior through real wiring. Fake only genuine system boundaries; do not mock project classes or assert private call sequences.
- Do not weaken tests or add speculative stress, fuzz, portability or security gates outside the agreed scope.
- A defect fix uses two conventional commits: the failing regression test, then the minimal fix. Keep both commits through merge. If a useful deterministic regression is impractical, explain why in the PR.
- Run focused JVM tests during iteration: `mvn test -pl <module> -am` (always pass `-am` so reactor dependencies are built). Native builds and real external services are not required on every edit.
- Before delivery, run relevant checks and report what was actually exercised. JVM success is not Native or real-terminal acceptance.
- Native-sensitive dependency, resource, packaging or terminal changes require native verification; a release requires the full JVM suite, Native tests and binary smoke.
- Tests must not depend on credentials or developer-machine state. Use temporary directories for test data.

## Git and worktrees

- Before each work segment: `git worktree list`, `git status --short`, `git branch --show-current`.
- Keep the main checkout on main. Work in your own `.worktrees/<agent>` directory, one task branch and PR at a time; never modify another agent's worktree.
- Start task branches from origin/main after fetch. A fresh local repository without a remote is the bootstrap exception.
- Stage only task-owned paths; never use git add -A, git add ., stash, reset/clean or checkout to discard unrelated changes.
- Commit completed, verified changes in the same task. Push the task branch and create the PR; never push main directly after initial repository bootstrap.
- Use conventional commits. Fix PRs keep test/fix commits through merge; do not squash them.
- After merge, park your own worktree detached on origin/main and delete only your own merged task branch. Keep the worktree's build state.
- Install local hooks once: `git config core.hooksPath "$(git rev-parse --show-toplevel)/.githooks"`. Use an absolute path.
- Local hooks prevent common mistakes; they do not replace remote access controls. No command can protect uncommitted files in a shared checkout.

## Credentials and release

- Never read, copy, print or export credentials. Use git and gh through their existing authentication; do not inspect tokens, keychains, credential helpers, or secret config values.
- Do not perform a real-service check when authorization or credentials are unavailable; name the unverified check.
- SemVer: feature = minor, defect/maintenance = patch, breaking change = major. Do not bump for intermediate work.
- Release flow: bump pom.xml through a PR; run JVM and Native verification; tag the approved commit `v<version>`; the release workflow builds and publishes that tagged version.
- The tag version must equal project.version. Do not overwrite tags or release a different commit from the one approved.
