Find What's Eating Your Disk.

Scan a directory tree once, get a size-sorted report, drill down interactively or export machine-readable JSON. One static binary, identical numbers on macOS, Linux and Windows.

Honest Numbers, Zero Dependencies

Engineered around predictable semantics and a single static binary.

🚀

Single Native Binary

Compiled ahead-of-time with GraalVM Native Image. No JVM, no install steps — drop it into CI containers, Alpine images or air-gapped servers.

🧹

Pure JDK Scanner

The scanning engine is Files.newDirectoryStream plus BasicFileAttributes and nothing else. One dependency in the whole tool — JLine's terminal layer, which is what makes the full-screen UI work on Windows too.

🧭

ncdu-Style Browsing

A line-based REPL instead of a curses UI: cd <n>, up, top, sort. Works in every terminal, including the classic Windows console and SSH.

📤

JSON Export

--json emits the full subtree with per-directory aggregates, written by a zero-reflection streaming writer — agents and CI can consume it directly.

⚖️

Honest Size Semantics

Apparent sizes for cross-platform parity, hardlinked content counted once per scan, symlinks never followed, unreadable paths skipped with a warning instead of aborting.

⚡

Parallel by Default

Directories fork into worker threads once a level is wide enough to pay for it, and stay inline below that, so small trees cost nothing extra. On a 59 GB, 660k-file tree: 3.2s versus ncdu's 8s.

Three Commands. That's the Point.

A full tree, a bounded ranking, or an interactive walk. Everything else is a flag.

scan dukit scan [path] [--depth <n>] [--exclude <glob>...] [--text]
Full directory tree, JSON by default

Walks the tree once and emits every directory with its size. The tree holds directories only — files fold into their parent's counters, so output tracks directory count instead of file count. --depth trims levels while aggregates still cover whole subtrees: on a real /Applications scan, all levels are 11 MB and --depth 2 is 30 KB. --text swaps JSON for a human tree.

top dukit top [path] [--limit <n>] [--files] [--min-size <size>] [--json]
Bounded ranking, streamed

Answers "what is big" without building a tree. Two bounded heaps keep only the largest entries, so memory tracks --limit, not the volume. --files ranks individual files instead of directories; --min-size 1G ignores anything smaller. Roughly 2 KB of JSON for 20 entries.

browse dukit browse [path] [--exclude <glob>...]
Interactive line-based explorer

Scans first, then takes over the terminal: alternate screen, arrow-key selection, enter to descend, backspace to return, s to cycle size → name → count. Always starts sorted by size with the biggest entry selected. Requires an interactive terminal — piped invocations fail fast with a hint toward scan.

Frequently Asked Questions

How do dukit's numbers compare to du or ncdu?

dukit reports apparent sizes — the sum of logical file sizes, like du --apparent-size. Hardlinked content counts exactly once per scan, symlinks are never followed, and directory inodes add nothing. Unreadable paths are collected as warnings while the scan continues, so a locked directory never hides the rest of the picture.

Why apparent sizes instead of allocated blocks?

The Java standard library exposes no portable allocated-block metric, and per-platform FFI would break the zero-dependency, zero-native-metadata guarantee this project is built on. Apparent sizes are also the only metric that means the same thing on APFS, ext4 and NTFS — the whole point of dukit being cross-platform.

Can dukit delete files like ncdu?

Not yet — and that is deliberate. Deletion is where an analyzer stops being safe to point at arbitrary paths; dukit v1 only reads. Machine-readable --json output makes it easy to script the cleanup you actually want, with your own confirmation rules.

Does the browser work over SSH and on Windows?

Yes. dukit browse is a line-based REPL rather than a full-screen curses UI, so it needs nothing but a working stdin: classic Windows console, Windows Terminal, tmux panes and SSH sessions all behave identically.
