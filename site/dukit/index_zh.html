单一原生二进制

GraalVM Native Image 提前编译。无需 JVM、无需安装步骤——直接放进 CI 容器、Alpine 镜像或离线服务器。

🧹

纯 JDK 扫描引擎

扫描引擎只有 Files.newDirectoryStream 与 BasicFileAttributes,没有别的。整个工具只有一项依赖——JLine 的终端层,它也是全屏界面能在 Windows 上跑起来的原因。

🧭

类 ncdu 交互浏览

行式 REPL 而非 curses 全屏:cd <n>、up、top、sort。所有终端通用,包括经典 Windows 控制台与 SSH。

📤

JSON 导出

--json 输出完整子树与每层聚合,由零反射流式写出器生成——Agent 与 CI 可以直接消费。

⚖️

诚实的尺寸语义

表观大小保证跨平台一致;符号链接永不跟随;不可读路径跳过并警告,不中断扫描。硬链接内容在 macOS 与 Linux 上同一扫描只计一次;Windows 的 java.nio.file 不暴露 fileKey,因此每个链接各计一次。

⚡

默认并行

某一层目录足够宽时分叉到工作线程,不够宽就留在当前线程串行处理,因此小目录树没有额外开销。实测 59 GB、66 万文件的目录树:3.2 秒,而 ncdu 需要 8 秒。

三个命令。这就是全部。

完整目录树、有界排行，或交互式浏览。其余一切都是选项。

scan dukit scan [路径] [--depth <n>] [--exclude <glob>...] [--text]
完整目录树，默认 JSON

一次遍历目录树,输出每个目录及其大小。树中只有目录——文件折叠进父目录的统计字段,因此体积只跟目录数相关,不再随文件数爆炸。--depth 裁剪层数,但聚合值始终覆盖完整子树:实测扫描 /Applications,全量 11 MB,--depth 2 只有 30 KB。--text 切换为人类可读树。

top dukit top [路径] [--limit <n>] [--files] [--min-size <大小>] [--json]
有界排行，流式计算

不建树就能回答"哪里最大"。两个有界堆只保留最大的条目,内存只跟 --limit 相关,与磁盘体量无关。--files 排行单个文件而非目录;--min-size 1G 过滤掉更小的项。20 条结果的 JSON 约 2 KB。

browse dukit browse [路径] [--exclude <glob>...]
行式交互浏览

先扫描,然后接管终端:备用屏幕、方向键选择、Enter 进入、Backspace 返回、s 循环切换 大小 → 名称 → 文件数。始终按大小降序、默认选中最大项。需要交互终端——管道调用会快速失败并提示改用 scan。

常见问题

dukit 的数字与 du、ncdu 相比如何?

dukit 报告表观大小——逻辑文件大小之和,相当于 du --apparent-size。同一扫描内硬链接内容只计一次,符号链接永不跟随,目录 inode 不额外计入。不可读路径以警告收集,扫描继续进行,一个加锁的目录不会遮住其余全貌。

为什么用表观大小而不是磁盘分配块?

Java 标准库没有跨平台的分配块指标,而逐平台 FFI 会破坏本项目赖以成立的零依赖、零原生元数据保证。表观大小也是唯一在 APFS、ext4 与 NTFS 上含义一致的指标——这正是 dukit 跨平台的意义所在。

dukit 能像 ncdu 一样删除文件吗?

目录可以删——但只能在交互界面里。选中目录按 d,看过确认页再按 y,目录会移入系统回收站(macOS 的 ~/.Trash、Linux 的 freedesktop Trash、Windows 的回收站)。dukit 绝不请求永久删除;Windows 上若回收站被禁用或已满,Shell 可能在自己警告后永久删除。这里刻意不提供 CLI 删除命令:只有当你能看见它来自哪棵树时,删除才是安全的。

浏览模式支持 SSH 与 Windows 吗?

支持。dukit browse 是行式 REPL 而非全屏 curses 界面,只需要可用的 stdin:经典 Windows 控制台、Windows Terminal、tmux 面板与 SSH 会话行为完全一致。
