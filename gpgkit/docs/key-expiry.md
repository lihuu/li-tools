# 密钥到期 runbook

**背景事实**：**每个 OpenPGP 密钥都有到期日**，你手里这把也不例外。
`gpgkit status` 会替你盯着它，`gpgkit extend` 用来在到期之前把日期往后挪。

这篇不催你现在做什么。它的目的是：**到期那天，你不用重新想一遍。**

（如果你的密钥还很新，下面大部分内容现在**只需要读一遍**，然后放这儿。）

---

## 先记住三件事

1. **到期前用 `gpgkit extend` 续期**，只改自签名，**不动密钥**。
2. **已经发布出去的签名不受影响。** 别人昨天验过、昨天发布的那份 `.asc`，明天还是验得过。
3. **到期不是密钥坏了，是它不能再签新东西了。** 区别很大——见下面。

---

## 到期那天会发生什么

### 已经发布的签名：不受影响

这是最容易被误解的一点，也是**不需要做任何补救**的一点。

签名的有效性判定依赖的是**签名当时的密钥状态**：这份签名是在密钥还有效的时候做的，
它就一直有效。续期、过期、甚至密钥后来被吊销——**都不会让一份已经做出的、时间戳在有效期内的
签名变成"假"**。

所以：

- 你过去发到 Maven Central 的每个版本，签名都还在；
- 别人 clone 下来 `gpg --verify` 或 `gpgkit verify`，结果不会因为你的密钥过期而变红。

**不需要重新签名、不需要重新发布旧版本。** 这一点想清楚了，处理续期的时候就不会慌。

### 新签名：开始失败

密钥一旦过期，**新的**签名会开始出问题：

- `gpgkit sign` 会签不出来，或者签出来的东西 `verify` 不过；
- git 签名会失败（`git commit -S` 报错）；
- 任何依赖"现在这把密钥还有效"的流程都断了。

`gpgkit status` 会告诉你还有多少天。**这就是它存在的意义**——不用你记得日期。

### 发布到 Maven Central：会被拒

发布流水线是这条链上**最敏感的一环**，因为它会当场签、当场传。密钥过期后：

- `maven-gpg-plugin` 签不出来 → 构建失败；
- 就算绕过了，Central 校验签名时会拒绝——**它不接受用一个已经过期的密钥做的新签名**。

这个失败发生在**发布那一刻**，也就是你最不想被打断的那一刻。所以：

> **别等到期再续。** `status` 一报 `WARN: 90 天内到期`，就去做下面第 2 步。

`gpgkit doctor` 里有专门一项看"剩余天数是否 < 90"，就是为了让这件事在
**发布之前**而不是**发布之时**被看到。

---

## 到期前：怎么续期

### 1. 先看还剩多久

```shell
gpgkit status
```

**你会看到**：每个密钥的到期日与剩余天数，末尾一句话结论。

- `OK` → 还早，什么都不用做。
- `WARN: 90 天内到期` → **现在就去续**，见下一步。
- `WARN: 没有可用签名密钥` → 不是到期问题，是密钥根本不在这台机器上，
  去 [migrate-to-new-machine.md](migrate-to-new-machine.md)。

### 2. 续期

```shell
gpgkit extend --expire 2y --publish
```

**你会看到**：**旧到期日 → 新到期日**，以及一条提醒——自签名改过了，公钥要重新 publish。
加了 `--publish` 就直接推了。

**为什么这是安全的**：`extend` **只改自签名，不动密钥本身**。密钥材料一个字节都没变，
指纹不变，所以：

- 所有已经发布的签名照旧有效（重复上面那条）；
- 别人手上你的公钥指纹不变，不需要重新建立信任；
- 只有"有效期"这个字段往后挪了。

这就是为什么**续期是正解，而不是生成一对新密钥然后通知全世界换掉旧的**。
后者是一次真正的迁移成本，前者只是改个日期。

### 3. 重新发布公钥

如果第 2 步没加 `--publish`，现在补上：

```shell
gpgkit publish
```

**你会看到**：推送到 keyserver 的结果。失败时会给出**可操作的下一步**
（换 keyserver、检查网络代理），不是干报错。

**为什么必须重推**：keyserver 上还挂着**旧的自签名**那份公钥。别人从 keyserver 拿到的是旧的，
会看到旧的到期日。不重推，续期就只对你本机有效。

### 4. 确认

```shell
gpgkit doctor
```

**你会看到**：`PASS/WARN/FAIL` 的逐条结论，其中"剩余天数"那条应该从 WARN 变回 PASS，
并且**真签一次并验回来**那一条是 PASS。

**这一步不要省。** 前面每一步都"看起来成功了"，跟"现在真的能签"是两件事。

### 5. 续期之后更新备份

自签名变了，**备份里那份是旧的**。

```shell
gpgkit backup --out ~/gpg-backup --dest onedrive:gpgkit
```

**你会看到**：回环校验通过，新的 `manifest.json`，新的还原命令。
把新密文按原来的规矩放进私人保管箱（[backup-placement.md](backup-placement.md)），
旧的可以清掉——**但要确认新的一份已经落到位、能还原之后**再清。

## 如果已经过期了

顺序不一样，但路子一样：

1. `gpgkit status` 确认是"过期"而不是"密钥不在本机"。
2. **`gpgkit extend` 续期。** 即使已经过期，续期通常仍然能成功——
   过期不等于不能用，而是需要重新签一份自签名把有效期挪到未来。
   无口令密钥不需要输入口令（见下节）。
3. 重推公钥（`--publish` 或 `gpgkit publish`）。
4. `gpgkit doctor` 确认恢复到能签。
5. **补做备份。**

**已经发布的签名仍然不用处理。** 这条在过期之后依然成立。

如果 `extend` 也失败了，别自己乱试 `gpg` 的底层参数——先跑 `doctor`，
把具体哪一步断的记下来。

## 无口令这件事（顺带说清）

用不用无口令密钥（生成时用 `%no-protection`）是**有意的取舍**，不是疏忽——但它是一道
选择题，不是所有人都该选同一边。下面只说这个取舍本身的两面。

**为什么有人选它**：发布流水线要**无头签名**。`maven-gpg-plugin` 配 `--pinentry-mode loopback`，
密钥没有口令，就不会弹 pinentry 卡在那里等一个永远不会来的输入。

**代价**：**私钥文件本身就是凭据**。拿到文件就等于拿到了身份——没有第二道。

**本工具的立场**：不因为难用就退回去加密钥口令，而是让"选了无口令"这件事
**有备份、有记录、有到期日**兜着：

- `backup` 默认给导出物加口令加密存起来（无口令密钥 ≠ 备份也无口令）；
- `status` / `doctor` 盯着到期日；
- 全程不打印私钥。

所以"无口令"不是没有防线，防线是**备份加密 + 到期管理**这两条。
这两条一断，无口令密钥就是裸奔——这就是为什么这篇 runbook 值得存在。

`gen --passphrase-file` 是支持带口令的密钥的。但带口令会让无头签名需要
`passphraseEnvName`，**用之前先想清楚**——这是一次真正的取舍，不是"更安全就选它"。

## 一页速查

| 时间点 | 做什么 |
|---|---|
| 平时（`status` 报 `OK`） | 读一遍这篇，然后忘掉它 |
| `status` 报 `WARN: 90 天内到期` | `gpgkit extend --expire 2y --publish` → `doctor` → 重新 `backup` |
| 到期当天及之后 | 同样的四步，顺序不变；已发布的签名依旧不用管 |
| 每次发布前 | `gpgkit doctor` |
