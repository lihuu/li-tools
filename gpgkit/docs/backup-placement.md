# 密文放哪、口令放哪

这篇回答一个问题：**备份做完了，那两个文件分别该放哪儿。**

答案是一句话：**密文和口令必须放在两个地方，两条路分开走。** 下面说清楚放哪儿、为什么、
以及哪些地方**绝对不要**放。

## 先分清是两个东西

`gpgkit backup` 会产生两样东西，它们长得很像"秘密"，但风险等级完全不同：

| | 是什么 | 泄露的后果 |
|---|---|---|
| **密文** | `.asc.gpg` 文件 + 旁边的 `manifest.json` | 还需要口令才能变成私钥。**单独泄露不等于身份丢失** |
| **口令** | `--generate-passphrase-to F` 写出的那个文件 | 口令 + 密文 = 完整的私钥。**两样凑齐就完了** |

所以整套安排的目标不是"把密文藏得多深"，而是**保证这两样永远不待在同一个地方**。
密文可以放在相对开放的地方，正是因为口令不在那儿。

## 通用建议

不管用什么工具，规则就三条：

1. **密文进云端保险箱。** 找一个**需要额外认证才能打开**的云端区域：云盘自带的保险箱
   （vault）功能、只有你持有密钥的加密归档、或者是另一台你自己控制的机器。
   密文已经是 AES256 加密过的，它需要的不是"藏得深"，而是"**多一道门**"——
   就算别人拿到了你的账号和设备，打开它还要再过一道。
2. **口令进密码管理器。** 1Password、Bitwarden、KeePassXC、Apple 的「密码」App 都行——
   挑一个**你本来就在用**的，不要为了这件事新装一个。
3. **两者必须分开。** 不同厂商、不同账号体系、不同入口。前两条都是为这一条服务的，
   这一条才是真正的防线。

## 一个可以照抄的例子

macOS 上现成的一对：**密文放 OneDrive 的私人保管箱，口令存进 Apple 的「密码」App。**
两个都是系统里已经有的东西，不用额外注册服务。用别的组合就把下面的名字换掉，规则不变。

**密文 → OneDrive 的私人保管箱（Personal Vault）。**

私人保管箱是 OneDrive 里一个**需要额外认证才能打开**的区域——就算别人拿到了你的
Microsoft 账号和设备，打开它还要再过一道。密文放这里，是"多一道门"而不是"藏起来"。

做法：

```shell
gpgkit backup --out ~/gpg-backup \
              --dest onedrive:gpgkit \
              --generate-passphrase-to ~/gpg-backup-passphrase.txt
```

`onedrive:` 会落到 `~/Library/CloudStorage/OneDrive-Personal/gpgkit`。
跑完 `~/gpg-backup` 和 OneDrive 里各有一份密文和一份 `manifest.json`。

**然后，需要你手动做一步**：把 OneDrive 里那份密文**拖进私人保管箱**。
放在 `OneDrive-Personal` 里的那份，只是本地同步目录里的一份副本，**它不在保管箱里**。

**口令 → Apple 的「密码」App。**

把 `~/gpg-backup-passphrase.txt` 里的口令，作为一条新的"密码"条目存进「密码」App，
名字写清楚，比如 `gpgkit backup passphrase (指纹后 8 位)`，备注栏按 `manifest.json` 里
那个「口令在哪」的字段写（写**位置**，不要写口令本身）。
存好之后，把那个明文 txt 文件删掉。

## 两条真实的约束（踩过，记下来）

**① Apple「密码」App 不放文件附件。** 它只适合放**口令**这种一行文本。
所以不要试图把密文文件塞进「密码」App——它没有附件功能，硬凑只会让你把密文挪到一个
更不好管理、更不好传的地方。**App 里只放口令，密文永远留在文件系统/云盘那条线上。**

**② 命令行看不到 OneDrive 的私人保管箱。** 私人保管箱**不在文件系统里挂一个普通目录**，
它要在 Finder（或 OneDrive 客户端）里**解锁之后才出现**。
这意味着：`gpgkit backup --dest onedrive:...` **写不进私人保管箱**，
`ls ~/Library/CloudStorage/` 里也永远看不到它。

这不是 gpgkit 的缺陷，也不是可以靠加一个参数解决的问题——**私人保管箱是人工开的门**。
所以流程里"把密文拖进保管箱"这一步，诚实地标成**人工步骤**：

```text
gpgkit backup --dest onedrive:gpgkit   ← 自动：写到 OneDrive-Personal
在 Finder 里解锁私人保管箱              ← 人工
把密文 + manifest.json 拖进去           ← 人工
```

**代价**：OneDrive 里会留下一份"还没进保管箱"的副本。备份做完当天就把它挪走，
别让两份密文在同一个地方躺着——这不是密码学问题，是**你自己半年后分不清哪份是最新的**的问题。

## 为什么"云盘同步密文"本身没问题

很多人对云盘存密钥有本能抵触。这里可以说清楚为什么这个安排是成立的：

1. **密文已经加密了。** 默认 AES256 对称加密，没有口令，云盘服务商拿到的就是一坨字节。
2. **口令不在同一处。** 这是关键。云盘被拖库、账号被盗、客户端同步泄露——
   这些事故暴露的是**密文**那一半。口令在密码管理器里，是**另一条**信任链。
3. **两边同时破才出事。** 攻击者需要"拿到云盘上的密文"**并且**"拿到密码管理器里的口令"。
   这是两个不同厂商、不同认证体系、不同入口的东西。

反过来说，这套安排唯一真正的弱点就是**你自己把两样凑到一起**：
把口令文件留在 `~/gpg-backup/` 密文旁边、把口令写进 `manifest.json`、或者把口令贴进备忘录取同一个名字。
**别做这三件事**，这套安排就是成立的。

`gpgkit backup` 在这一点上是帮你的：它生成的 `manifest.json` 里那一栏是**"口令在哪"的备注**，
是**给你写位置用的**，工具**不会**把口令写进去。这是有意的设计，不是你忘了开某个选项。

## 绝对不要做的事

| 不要 | 为什么 |
|---|---|
| 把**私钥明文**放云盘 | 明文私钥就是身份本身，云盘同步会把它复制到你所有登录过的设备 |
| 把**私钥明文**提交进任何 git 仓库 | 一旦推上去，历史里就有；删掉文件也删不掉历史。公开仓库几分钟内就会被扫走 |
| 把**私钥明文**放进 CI secret / 构建环境变量 | CI 日志、缓存、fork 的 PR 都可能把它带出去；而且无口令密钥进了 CI，等于把签名能力交给了那个环境 |
| 把**口令**和密文放同一处 | 见上文——这一条会一次性抹掉整套安排的唯一防线 |
| 把**口令**写进 `manifest.json` 或备份目录里的任何文件 | 备份目录会被整个同步、整个拷贝到新机器 |

gpgkit 在输出里不打印私钥、口令、token，也在 `backup` 里坚持回环校验——
但它**管不到你把文件放哪儿**。这一步是你的。

## 自查

半年后重新面对这套东西时，问自己四个问题：

1. 密文在云端保险箱里吗？（**是**——不是在同步目录里躺着。用上面那个例子的话：
   是在私人保管箱里，不是在 `OneDrive-Personal` 里）
2. 口令在密码管理器里吗？（**是**——不是还在某个 txt 文件里）
3. 这两样在同一个地方出现过吗？（**没有**）
4. `manifest.json` 里那一栏写的是**位置**，不是口令本身吗？（**是**）

有任何一个答"不是"，先把它改成"是"，再做别的。
