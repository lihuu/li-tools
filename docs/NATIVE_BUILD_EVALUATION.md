# Native Image 编译速度优化评估

日期：2026-10-22。基线提交：[`755052e`](https://github.com/lihuu/li-tools/commit/755052e7001ae07dc94be2bfb81d07cae800d258)。

本文整理本地实验与 Pi 独立复核的结论，作为后续优化的决策记录。本次仅新增文档，正式构建脚本、安全配置和发布工作流均未改动。

## 决策

- **保持 `-O3` 与现有安全策略。** 切换优化等级在本机仅节省约 2 秒，不作为下一步迁移方向。
- **优先评估一次 reactor 打包，消除重复 Maven 调用。** 落地时必须同时让各工具脚本能够显式跳过 Maven；只在工作流预打包无法消除脚本内的重复工作。
- **受控并行保留为 macOS 自托管候选。** 本机两次测量均缩短了整体墙钟时间，但 Linux、Windows 和资源较少的 runner 尚未验证。
- Pi 的独立验证结论为**有条件通过**：实验方向与已测功能成立，尚不能承诺正式 CI 的提速比例，也尚未完成优化迁移。

## 环境与测量边界

实验使用 macOS ARM64、14 个逻辑 CPU、GraalVM CE 25.0.2；每个 Native Image 进程的 JVM 堆上限为 `-J-Xmx4g`。比较流程时保持源码、`-O3`、安全配置和各工具所需 Native 参数一致。

下文“构建流程总时间”仅包含 Maven 准备与 Native 编译，不包含测试、依赖首次下载、归档上传或发布。各套实验的网络模式、线程数和计时范围分别标注，不能混算。

所谓“冷 target”是清除实验副本生成的 `target` 后构建；Maven 依赖已缓存，**不是首次联网构建**。所有功能测试使用临时合成数据与回环服务，不依赖真实凭据或服务。

## 1. 优化等级：继续使用 O3

以 certkit 的同一 JAR、安全配置和 4 GB 堆进行比较。使用本机默认 14 线程，各模式构建 3 次，顺序轮换；计时仅包含 Native Image 进程。

| 模式 | 构建中位秒数 | 最小–最大秒数 | 相对 O3 节省 | 产物大小（十进制 MB） |
|---|---:|---:|---:|---:|
| `-O3` | 20.44 | 20.07–21.78 | — | 28.95 |
| `-Os` | 18.62 | 18.37–19.04 | 8.9% | 25.37 |
| `-Ob` | 18.34 | 18.27–18.88 | 10.3% | 30.94 |

`-Os` 的体积收益明确；`-Ob` 与 `-Os` 的中位数只差约 0.28 秒，耗时区间重叠，不能认定存在稳定优势。三个模式均通过该轮 certkit 基础功能检查，但这不等于全部业务吞吐或跨平台验收。

另一轮固定 4 线程的 O3/Os 实验得到 30.28/26.71 秒，每模式仅 1 次；不能与本表混算。该轮弱证书 TLS 对照未能提供有效结论，未计入通过项。

**结论：目标是加快编译，当前收益不足以推动优化等级迁移；保持 O3，转向构建编排。** 此模式比较是前序实验记录，Pi 本轮重点复核的是下述构建流程。

## 2. Maven 准备：重复工作可以消除

离线 `mvn -o --batch-mode -DskipTests`，每种状态各 3 次，顺序交替。基线为 1 次 `install -pl cli-common -am` 加 3 次 `package -pl <tool> -am`；候选为根目录 1 次完整 reactor `package`。

| 状态 | 基线四次调用中位秒数 | 一次 reactor 中位秒数 | 减少秒数 |
|---|---:|---:|---:|
| 冷 target | 8.38 | 3.60 | 4.79 |
| target 不变立即重复 | 5.41 | 2.23 | 3.18 |

三工具 JAR 的条目集合与内容 SHA-256 均一致：gpgkit 308 项、certkit 274 项、tokenkit 457 项。Pi 独立复算确认内容等价。

reactor `package` 不执行 `install`，不会像基线一样把本项目产物安装到本地 Maven 仓库。当前发布产物打包不依赖这些本地安装件；但必须继续保留单工具脚本的 `-pl <tool> -am` 路径，使其能够独立准备依赖。

**3–5 秒是本机离线口径，不能直接作为 CI 承诺。** 正式 [release.yml](../.github/workflows/release.yml) 和各工具脚本没有设置离线模式。Pi 的补测中，同一缓存下四次 Maven 调用离线为 10.464 秒、联网为 33.058 秒；网络/元数据检查会改变耗时，单次差值也不能外推。

## 3. 完整编译流程：本机并行有收益

以下三套流程的 Maven 均为离线模式。实验直接控制 Maven 与 Native Image 调度，**并非未经修改地执行正式发布工作流**。

| 流程 | Maven 准备 | Native 调度 | 首轮总秒数 | 相对首轮基线减少 | Pi 反序重跑秒数 |
|---|---|---|---:|---:|---:|
| 基线模型 | 1 install + 3 package | 串行，每次默认 14 线程 | 61.897 | — | 61.032 |
| 统一打包＋串行 | 1 reactor package | 串行，每次默认 14 线程 | 56.286 | 9.1% | 56.786 |
| 统一打包＋受控并行 | 1 reactor package | 3 进程同时，各 `ActiveProcessorCount=4` | 43.771 | 29.3% | 43.039 |

首轮顺序为基线→统一串行→并行；Pi 重跑为并行→统一串行→基线。第二轮统一串行减少约 7.0%，并行减少约 29.5%。反序后方向一致，降低了执行顺序造成收益假象的疑虑；每流程合计仍只有 2 个全流程样本，不能排除其他负载与缓存影响。

这里的 4 是每个构建 JVM 的 `ActiveProcessorCount` 设置，不代表进程总共只有 4 个线程；仍有 JIT、GC 等线程。并行缩短的是多个工具一起构建的墙钟时间，不代表单个工具编译更快。

三个工具在三套流程中的 Native 文件大小相同：

| 工具 | 字节数 |
|---|---:|
| gpgkit | 16,781,800 |
| certkit | 28,953,464 |
| tokenkit | 24,104,696 |

Native SHA-256 不同，**不能声称二进制逐字节一致**。Pi 在同目录、同输入、同命令重建时也观察到哈希不同，因此哈希差异本身不能证明流程改变了行为；行为证据来自所列功能测试，也不代表所有未测路径等价。

### 实施时必须同时处理脚本

各工具 `build-native.sh` 当前均无条件执行 Maven。工作流先统一打包，再原样调用三个脚本，会继续执行三个模块的 Maven 生命周期。

Pi 在临时副本中比较了三种实际调用方式，各 1 次：

| 调用方式 | 总秒数 |
|---|---:|
| 安装 common，再调用三个原始脚本 | 76.855 |
| 一次打包，再调用跳过内部 Maven 的临时脚本 | 62.911 |
| 一次打包，再调用三个原始脚本 | 77.895 |

此补测的外层 Maven 使用 `-o`，原始脚本内部仍是联网 Maven，计时包含 Native 编译。它与上面的全离线流程口径不同；日志字段 `maven_seconds` 也包含了整个脚本时间，不能当作纯 Maven 耗时。仅预打包方案未显示收益，约 1 秒的差异不足以认定稳定退化。

**建议采用显式跳过开关或显式 Native 阶段入口。** 默认单独运行脚本时仍执行 Maven；工作流在同次任务成功准备全部 JAR 后，显式进入 Native 阶段，缺失输入时失败。临时补测用“JAR 已存在”跳过 Maven 仅证明减少重复调用的方向；不应照搬到正式脚本，以免复用过期产物。

### 并行资源边界

Pi 的一次并行重跑以约 0.25 秒间隔采样 113 点，记录 Native 构建进程合计 RSS 峰值约 **3777 MiB**；各进程构建日志报告峰值约 1.30/1.65/1.53 GB。

这是该次采样观察值，可能漏过短峰，也不是包含 Maven、系统和 runner 服务的整机峰值。`Xmx4g` 是堆上限，不是预留量；RSS 也不等于堆使用量。不能据此认定小 runner 已有足够余量，或直接推导应把堆上限降为 2 GB。

当前只支持将此方案作为资源充足的 macOS 自托管环境候选。Linux/Windows 应先独立测量，再决定单机并行或按工具拆分 runner；拆任务可能增加准备开销与总 runner 时间，尚未证明更优。

## 4. 功能与安全验证

原流程实验完成 9 次 Native 构建（三流程×三工具）。Pi 独立重跑流程、JVM 测试及关键冒烟路径，未发现所列功能的假通过。

| 已覆盖路径 | 结果与边界 |
|---|---|
| 全量 JVM | 131 项，0 失败、0 错误、0 跳过；cli-common 36、gpgkit 38、certkit 12、tokenkit 45 |
| Native help | 原实验 9 个二进制入口通过 |
| gpgkit | 临时新建测试密钥，签名、正确验签、篡改拒绝 |
| certkit | 自签名生成、PEM/DER 指纹一致、PKCS12 转换、缺失文件退出码；Pi 另检查 PKCS12 含私钥条目，未验算法强度 |
| TLS | 临时信任库下 TLS 1.2 成功、TLS 1.0 拒绝；Pi 补充错误 CA、空信任库、未指定信任库、未受信服务端证书等失败对照 |
| tokenkit | 临时库与合成主密钥 AES 往返、PBKDF2 加密 bundle、跨测试主密钥导入、错口令拒绝、删除 |
| macOS 归档 | 9 个 tar.gz 的成员名、可执行权限、内部二进制哈希与 SHA256SUMS 校验 |

### 安全修复必须保留

历史修复见 [PR #11](https://github.com/lihuu/li-tools/pull/11)。当前 [pruned-security.properties](../scripts/pruned-security.properties) 先包含构建 JDK 的完整 `java.security`，再覆盖 provider 列表，并以空 `security.provider.7=` 结束连续列表。三个 Native 脚本通过 `set --` 与 `"$@"` 传入安全属性参数，保护含空格路径。

Pi 观察到：移除 `include` 后，JDK TLS 与证书路径算法限制属性丢失；用该配置反事实构建的 Native certkit 能连接同一 TLS 1.0 测试服务，而当前三套产物拒绝。因此保留 JDK 安全策略有实际作用，本轮编排实验没有削弱该修复。

certkit 的证书生成/转换使用外部 OpenSSL，并不意味着所有安全行为都由系统工具负责：证书读取、Java TLS 与信任链检查仍有 Java 执行路径。**TLS 1.0 拒绝、弱证书拒绝和完整 PKIX 验收不是同一项结论。** 现有对照支持已测协议策略与信任链路径生效；历史弱证书 fixture 未得到有效对照，不计入通过项，也不作全面安全保证。

## 5. 后续最小步骤

以下为建议，尚未实施：

1. 同时调整发布编排与工具脚本：一次 reactor 打包，显式跳过重复 Maven，保留默认独立构建路径；保持 O3、安全配置、路径引用和各工具 Native 参数。
2. 在改后的真实入口验证：干净副本、独立工具调用、显式跳过且缺 JAR、带空格路径；确认不会自动使用旧 JAR，也不会并行写 Maven 共享输出。
3. 用正式的联网 Maven 口径复测基线与候选，顺序轮换，分别记录 Maven、Native、整段墙钟与资源占用。先验证统一打包，再单独评估并行，不同时改堆上限。
4. Linux、Windows 各验证串行基线与统一打包候选，完成相关 Native 冒烟及对应归档校验，再决定是否推广并行。

未完成的验收包括：本轮 Linux/Windows Native 与并行、实际 GitHub Actions、新发布链路、所有 CLI 选项、真实服务/凭据/系统信任变更及有效弱证书 TLS 对照。历史 CI [run 39619546269](https://github.com/lihuu/li-tools/actions/runs/39619546269) 对应更早提交 `13a8b48`，只作背景，不能证明当前优化效果。
